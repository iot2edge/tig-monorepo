The mental map

Start with these four ideas. Most Kubernetes details are just combinations of them.

C

Container

A packaged app with everything it needs to run. Docker builds images; Kubernetes runs containers from those images.

P

Pod

The smallest thing Kubernetes schedules. Usually one app container plus its shared network and storage space.

D

Deployment

A controller that keeps the desired number of Pods alive and manages updates without manual babysitting.

S

Service

A stable network name and IP for a changing set of Pods. Apps talk to Services instead of chasing Pod addresses.

Lecture 1: Why Kubernetes exists

Learning objectives

  • Understand the problem Kubernetes solves.
  • Explain the difference between a container runtime and a container orchestrator.
  • Describe desired state in plain language.

Imagine you have a small web application. At first, you copy the application onto one server and run it. If it crashes, you SSH into the server and restart it. If traffic grows, you buy a bigger server or copy the app to another machine. This can work for a toy project, but production systems quickly become messier: several services, several versions, multiple machines, failed disks, traffic spikes, configuration changes, deployments, rollbacks, and security updates.

Containers solve one part of the problem. A container image packages your application and its runtime dependencies so it can run consistently on different machines. But a container image does not decide which machine to run on. It does not restart itself after a node failure. It does not automatically create three copies, roll out version 2, roll back to version 1, or give other services a stable address to call.

Kubernetes is the orchestration layer around containers. You give Kubernetes a desired state: "I want three replicas of this app, using this image, with this port exposed." Kubernetes continuously compares that desired state with the real state of the cluster. When reality differs, Kubernetes acts.

Imperative versus declarative

An imperative instruction says exactly what to do: "start this container on server A." A declarative instruction says what final state should exist: "there should be three running replicas of this app." Kubernetes is powerful because it keeps pursuing the declared final state even after crashes, restarts, and infrastructure changes. 

# Imperative style: do this one action
docker run -p 8080:80 nginx

# Declarative Kubernetes idea: make this state true
kubectl create deployment web --image=nginx
kubectl scale deployment web --replicas=3

Checkpoint: Docker runs containers. Kubernetes decides how containers should be scheduled, restarted, connected, scaled, and updated across a cluster.

Lecture 2: Cluster, nodes, and the control plane

Learning objectives

  • Identify the control plane and worker nodes.
  • Explain what the API Server, Scheduler, controllers, etcd, and kubelet do.
  • Trace what happens after you run kubectl apply.

A Kubernetes cluster is a set of machines working together. The machines are called nodes. Some nodes run the control plane, which is responsible for cluster decisions. Worker nodes run your application workloads. In local learning tools like Minikube or Kind, everything may run on your laptop, but the logical parts are still the same.

The API Server is the front door. When you run kubectl, you are talking to the API Server. The API Server validates your request and stores the desired object state. etcd is the strongly consistent database where cluster state is kept. The Scheduler watches for Pods that do not yet have a node and picks a suitable node. Controllers watch for differences between desired state and real state, then create or update objects to close the gap.

Each worker node runs a kubelet. The kubelet is the node agent. It talks to the container runtime, starts containers, reports status, and makes sure the Pods assigned to that node are running as expected.

Request flow

  • You run kubectl apply -f deployment.yaml.
  • The API Server validates and stores the Deployment.
  • The Deployment controller creates a ReplicaSet.
  • The ReplicaSet creates Pod objects.
  • The Scheduler assigns each Pod to a node.
  • The kubelet on each node starts the containers.
kubectl get nodes
kubectl get pods -A
kubectl cluster-info
kubectl describe node <node-name>

Common mistake: thinking kubectl directly starts containers. It does not. It sends requests to the API Server; Kubernetes components react from there.

Lecture 3: Pods and YAML

Learning objectives

  • Define a Pod and explain why it is not a virtual machine.
  • Read the basic structure of a Kubernetes manifest.
  • Create, inspect, log, and delete a Pod.

The smallest unit Kubernetes schedules is a Pod. A Pod usually contains one application container, although it can contain more than one tightly related container. Containers inside the same Pod share network space, which means they can talk to each other through localhost.

Kubernetes objects are usually written as YAML manifests. A manifest says what kind of object you want, gives it metadata like a name and labels, and defines the desired spec. The common shape is apiVersion, kind, metadata, and spec. 

apiVersion: v1
kind: Pod
metadata:
  name: hello-pod
  labels:
    app: hello
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80

How to read this manifest

  • apiVersion tells Kubernetes which API group/version this object belongs to.
  • kind says the object type: here, a Pod.
  • metadata.name gives the object a name.
  • metadata.labels adds searchable identity tags.
  • spec.containers describes the containers that should run inside the Pod.
kubectl apply -f pod.yaml
kubectl get pods
kubectl describe pod hello-pod
kubectl logs hello-pod
kubectl delete pod hello-pod

Common mistake: creating raw Pods for long-running apps. Learn Pods first, but use Deployments for real applications because Deployments replace failed Pods.

Lecture 4: Deployments and the control loop

Learning objectives

  • Understand why Deployments are preferred over raw Pods.
  • Explain replicas, ReplicaSets, rollout, and rollback.
  • Scale an app and watch Kubernetes repair it.

You can create a Pod directly, but in real applications you usually create a Deployment. A Deployment says which container image to run and how many replicas you want. If a Pod crashes or is deleted, the Deployment controller makes a replacement.

This is the Kubernetes control loop in action. You declare desired state, Kubernetes observes actual state, and controllers act to close the gap. If you ask for three replicas and only two are running, Kubernetes creates another. If you update the image version, Kubernetes performs a rollout.

This is why deleting one Pod in a Deployment does not delete the application. The controller sees that the desired replica count is no longer satisfied and creates a new Pod. 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80

Important relationship

A Deployment owns a ReplicaSet. A ReplicaSet owns Pods. The Pod template inside the Deployment defines what new Pods should look like. When you change the template, such as changing the image version, Kubernetes creates a new ReplicaSet and performs a rollout. 

kubectl apply -f deployment.yaml
kubectl get deploy,rs,pod
kubectl scale deployment web --replicas=5
kubectl set image deployment/web nginx=nginx:1.28
kubectl rollout status deployment/web
kubectl rollout undo deployment/web

Checkpoint: if you delete a Pod owned by a Deployment, Kubernetes creates a replacement because the desired replica count still says that Pod should exist.

Lecture 5: Services and networking

Learning objectives

  • Explain why Pod IPs are not stable enough for app-to-app communication.
  • Connect labels, selectors, and Services.
  • Understand ClusterIP, NodePort, LoadBalancer, and Ingress at a beginner level.

Pods are replaceable. Their IP addresses can change whenever Pods are recreated. That is a problem if one application needs to call another. A Service solves this by giving a stable network name and address to a changing group of Pods.

Services use labels and selectors. Pods have labels like app: web. A Service selector can say "send traffic to Pods with app: web". The Service stays stable even when individual Pods come and go.

The beginner Service types are ClusterIP, NodePort, and LoadBalancer. ClusterIP is internal to the cluster. NodePort exposes a port on nodes. LoadBalancer asks the cloud provider for an external load balancer. Ingress is commonly used for HTTP routing into Services. 

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

Traffic path

  • A client calls http://web from inside the cluster.
  • Cluster DNS resolves web to the Service.
  • The Service finds Pods matching app: web.
  • Traffic is forwarded to one healthy matching Pod.
kubectl get svc
kubectl get endpoints web
kubectl run curl --image=curlimages/curl -it --rm -- sh
curl http://web

Common mistake: Service selector does not match Pod labels. If a Service has no endpoints, check labels first with kubectl get pods --show-labels.

Lecture 6: Configuration, storage, and health

Learning objectives

  • Separate container image from environment-specific configuration.
  • Know when to use ConfigMaps, Secrets, and Volumes.
  • Understand readiness and liveness probes.

Application images should be reusable across environments. Configuration should usually live outside the image. Kubernetes gives you ConfigMaps for non-secret settings and Secrets for sensitive values. These can be exposed as environment variables or mounted as files.

Storage is more complex because Pods are temporary. If a Pod disappears, files inside the container can disappear too. For persistent data, Kubernetes uses Volumes, PersistentVolumes, and PersistentVolumeClaims. This lets a workload request storage without hard-coding the exact disk.

Health checks are called probes. A readiness probe tells Kubernetes whether a container is ready to receive traffic. A liveness probe tells Kubernetes whether a container should be restarted. 

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  APP_MODE: learning
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata:
  name: web-secret
type: Opaque
stringData:
  API_KEY: change-me

Using config in a Deployment

envFrom:
  - configMapRef:
      name: web-config
  - secretRef:
      name: web-secret

Probes in plain language

  • Readiness: "Should this Pod receive traffic right now?"
  • Liveness: "Is this container stuck badly enough that Kubernetes should restart it?"
  • Startup: "Give this slow-starting app more time before liveness checks begin."
readinessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 10

Common mistake: putting every setting in the container image. Build the image once, then use ConfigMaps, Secrets, and environment-specific manifests to change runtime behavior.

Lecture 7: Debugging and the full deployment story

Learning objectives

  • Build a first-response debugging routine.
  • Recognize common Pod failure states.
  • Explain the complete path from YAML to running app.

When something breaks, start by asking Kubernetes what it sees. Use kubectl get for status, kubectl describe for events and details, and kubectl logs for application output. Common beginner failures include bad image names, missing environment variables, failing probes, insufficient resources, and Services selecting the wrong Pods.

The full story is this: you write desired state in YAML, apply it through the API Server, Kubernetes stores it, controllers notice what needs to exist, the Scheduler places Pods on nodes, kubelets run containers, and Services give stable network access to those Pods.

Debugging routine

kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl get events --sort-by=.lastTimestamp
kubectl get deploy,rs,pod,svc
kubectl describe svc <service-name>

Common statuses

  • ImagePullBackOff: Kubernetes cannot pull the image. Check image name, tag, registry, and credentials.
  • CrashLoopBackOff: the container starts, crashes, and restarts repeatedly. Check logs and command arguments.
  • Pending: the Pod has not been scheduled. Check resources, node availability, taints, and storage claims.
  • Running but not ready: the container is alive, but readiness checks are failing.

Final story to memorize

You write YAML that describes desired state. kubectl sends it to the API Server. The API Server stores it in etcd. Controllers create the needed child objects. The Scheduler assigns Pods to nodes. Kubelets start containers. Services and Ingress route traffic. Probes and controllers keep checking whether reality still matches the desired state.

If you can explain Pod, Deployment, Service, ConfigMap, Secret, Volume, probe, and rollout, you have the foundation needed to keep learning Kubernetes without feeling lost.

Seven-day lecture plan

Each day is designed for about 90 to 150 minutes: one lecture block, one hands-on lab, and one checkpoint.

Hands-on labs

Use Minikube, Kind, Docker Desktop Kubernetes, or any disposable learning cluster.

Lab 1: run something

Create a Deployment, expose it, and open it locally.

kubectl create deployment hello --image=nginx
kubectl expose deployment hello --port=80 --type=NodePort
kubectl get pods,svc

Lab 2: scale and heal

Ask Kubernetes for three copies, delete one, and watch it come back.

kubectl scale deployment hello --replicas=3
kubectl get pods -w
kubectl delete pod <one-pod-name>

Lab 3: inspect a failure

Break an image name, read the events, fix it, and explain the status.

kubectl set image deployment/hello nginx=nginx:badtag
kubectl describe pod <new-pod-name>
kubectl rollout undo deployment/hello

Vocabulary you will actually use

Short definitions beat memorizing documentation pages on week one.

Core terms

ManifestA YAML file that describes desired cluster state.
NamespaceA named boundary for organizing resources inside one cluster.
ReplicaSetThe lower-level object that keeps a number of matching Pods alive.
ConfigMapNon-secret configuration mounted into Pods or exposed as environment variables.
SecretSensitive values stored separately from app images and manifests.
IngressHTTP routing from outside the cluster to Services inside the cluster.
ProbeA health check Kubernetes uses to know whether a container is ready or alive.
Resource limitA CPU or memory boundary that stops one workload from consuming too much.
RolloutA controlled update from one version of a Deployment to another.
