The mental model

Transformers are about choosing useful context. vLLM is about serving that context efficiently.

T

Tokens

Models do not see words directly. Text is split into token IDs, then mapped into vectors called embeddings.

A

Attention

Each token asks which other tokens matter right now. Query, key, and value vectors make that scoring possible.

K

KV cache

During generation, old key and value vectors can be reused instead of recomputed for every new token.

V

vLLM

An inference engine that schedules many requests, manages KV cache memory, and exposes model serving APIs.

Lecture 1: What a Transformer is trying to do

Learning objectives

  • Understand what next-token prediction means.
  • Explain tokens, token IDs, embeddings, and context length.
  • Describe why text must become vectors before a neural network can process it.

A Transformer language model is trained to solve a very simple-looking problem: given a sequence of tokens, predict the next token. If the prompt is "The capital of France is", the model should assign high probability to a token like " Paris". This small objective becomes powerful because the model sees huge amounts of text. To predict the next token well, it has to learn grammar, facts, style, reasoning patterns, and relationships between ideas.

The model cannot process raw text directly. First, text is split into tokens. A token can be a word, part of a word, punctuation, whitespace, or a code fragment depending on the tokenizer. Each token maps to an integer ID in the model vocabulary. That ID is then looked up in an embedding table to produce a vector.

The embedding vector is the model's starting representation of the token. At the beginning, the vector mainly identifies the token. After passing through Transformer layers, the vector becomes context-aware. The token "bank" should represent different meaning in "river bank" and "bank account"; attention is the mechanism that lets the model use neighboring tokens to make that distinction.

Tokenization example

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("gpt2")
text = "Transformers serve tokens."

print(tokenizer.tokenize(text))
print(tokenizer(text)["input_ids"])

Key vocabulary

  • Vocabulary: the full set of tokens the model can represent.
  • Token ID: the integer assigned to a token.
  • Embedding: the learned vector for a token ID.
  • Context length: the maximum number of tokens the model can consider at once.

Checkpoint: if someone says "the model reads words", correct it to "the model receives token IDs, turns them into vectors, and predicts the next token."

Lecture 2: Attention without the scary math

Learning objectives

  • Explain query, key, and value with intuition.
  • Understand why attention weights mix information between tokens.
  • Describe causal masking in decoder-only language models.

Self-attention answers this question for every token: "which other tokens should I use to update my current representation?" Each token creates three learned vectors from its current representation: a query, a key, and a value. A query is what the token is looking for. A key is what the token offers for matching. A value is the information that gets blended into the output if the match is strong.

The model compares queries against keys to create attention scores. After scaling and softmax, those scores become attention weights. A high weight means "use more information from this token." The output for a token is a weighted combination of value vectors. This is how information moves across positions in the sequence.

In text generation, attention is usually causal. Token 5 can look at tokens 1 through 5, but not token 6. That prevents the model from seeing the future while learning or generating.

The compact formula

# X is the sequence of token vectors
Q = X @ Wq
K = X @ Wk
V = X @ Wv

scores = Q @ K.T
scores = apply_causal_mask(scores)
weights = softmax(scores)
output = weights @ V

Common beginner mistake

Attention is not a database lookup and not human attention. It is differentiable vector matching. The model learns the projections that make useful tokens score highly for a given context.

Checkpoint: explain why "The animal did not cross the street because it was tired" needs context to decide what "it" refers to.

Lecture 3: Inside one Transformer block

Learning objectives

  • Identify attention, MLP, normalization, and residual connections.
  • Explain what multi-head attention adds.
  • Understand why blocks are stacked many times.

A Transformer is a stack of repeated blocks. A block usually has attention, an MLP, normalization, and residual connections. Attention moves information between token positions. The MLP transforms the information at each token position after attention has mixed the context.

Residual connections let the model add improvements to the previous representation instead of replacing it completely. Normalization helps keep values stable across many layers. With many stacked blocks, the model can build richer representations step by step.

Block skeleton

# One common decoder block shape
x = x + self_attention(layer_norm(x))
x = x + mlp(layer_norm(x))

Multi-head attention means the model runs several attention operations in parallel. Each head can learn a different pattern: one may track nearby syntax, another may track matching brackets in code, another may track names and references. The heads are combined so the layer can use multiple relationship types at once.

What changes through layers

  • Early layers often represent local patterns such as punctuation, phrase shape, or nearby dependencies.
  • Middle layers can combine broader context and structure.
  • Later layers prepare representations that are useful for predicting the next token.

Mental sentence: attention moves information between tokens; the MLP transforms information inside each token; residuals keep the path stable; stacking blocks builds depth.

Lecture 4: How generation works

Learning objectives

  • Explain logits, probabilities, and sampling.
  • Distinguish greedy decoding, temperature, top-k, and top-p.
  • Understand why LLMs generate one token at a time.

After the final Transformer layer, the model produces logits. Logits are raw scores for every possible next token in the vocabulary. The model can pick the highest-scoring token, or it can sample from likely tokens to produce more varied output.

Temperature changes how random sampling feels. Low temperature makes the model more conservative. High temperature makes it more varied, but also more likely to make strange choices. Generation repeats one token at a time: predict, append, predict again, and stop when a stop condition is reached.

Decode loop

tokens = tokenizer(prompt)

while len(tokens) < max_tokens:
    logits = model(tokens)
    next_token = sample(
        logits[-1],
        temperature=0.7,
        top_p=0.9
    )
    tokens.append(next_token)
    if next_token == stop_token:
        break

Sampling settings

  • Greedy: always choose the highest-scoring next token.
  • Temperature: controls how sharp or flat the probability distribution feels.
  • Top-k: sample only from the k most likely tokens.
  • Top-p: sample from the smallest set of tokens whose total probability reaches p.

Common mistake: expecting the whole answer to appear in one model call. Internally, generation is repeated next-token prediction.

Lecture 5: Why inference gets expensive

Learning objectives

  • Separate prefill from decode.
  • Explain KV cache and why it saves compute.
  • Reason about latency, throughput, and memory pressure.

Inference has two major phases. Prefill processes the prompt tokens you already have. Decode generates new tokens one by one. Long prompts make prefill heavier; long answers make decode last longer.

The KV cache stores key and value vectors from previous tokens. Without it, the model would recompute the same attention information again and again. With it, generation is faster, but memory usage grows with the number of requests and tokens.

This is why serving LLMs is also a systems problem. A server has to balance latency, throughput, GPU memory, batching, and fairness between active users.

Prefill versus decode

  • Prefill: process all prompt tokens and build initial KV cache.
  • Decode: generate one new token, update KV cache, repeat.
  • Time to first token: strongly affected by prefill and queueing.
  • Tokens per second: strongly affected by decode efficiency and batching.
# Rough intuition, not an exact formula
prompt_cost grows with prompt_tokens
decode_cost grows with generated_tokens
kv_cache_memory grows with active_requests * sequence_length * layers

Why KV cache helps

Suppose a prompt has 1,000 tokens and the model generates token 1,001. For token 1,002, the first 1,001 tokens are still the same. The model should not recompute all previous keys and values from scratch. The KV cache stores them so each decode step can focus on the new token plus cached context.

Checkpoint: long prompts mainly increase prefill work and KV-cache memory; long answers mainly extend the decode loop.

Lecture 6: What vLLM does

Learning objectives

  • Understand vLLM as an inference engine, not a new model architecture.
  • Explain OpenAI-compatible serving, continuous batching, and PagedAttention.
  • Start a small vLLM server and call it with HTTP.

vLLM is an inference and serving engine for large language models. Instead of manually loading a model and writing your own request scheduler, vLLM can run a server that accepts requests through an OpenAI-compatible API.

vLLM focuses on keeping the GPU busy and using memory efficiently. Continuous batching means the server can add new requests while other requests are still generating. This is better than waiting for a whole batch to finish before starting new work.

vLLM is also known for PagedAttention, which manages KV cache memory in blocks. The intuition is similar to paging in operating systems: requests can use blocks of memory as needed, which reduces waste when requests have different lengths or finish at different times.

Serving a model

pip install vllm

vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --host 0.0.0.0 \
  --port 8000

Calling the server

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "messages": [
      {"role": "user", "content": "Explain KV cache simply."}
    ],
    "temperature": 0.3
  }'

What vLLM is doing around the model

  • Accepting API requests and validating generation parameters.
  • Scheduling many active requests onto GPU work.
  • Managing KV-cache memory efficiently.
  • Running prefill and decode steps.
  • Returning complete or streamed responses.

Common mistake: thinking vLLM trains or improves the model. vLLM serves existing models efficiently.

Lecture 7: The full path from prompt to response

Learning objectives

  • Trace a request from HTTP input to generated text.
  • Connect model internals to serving-system behavior.
  • Know what to measure in a basic serving demo.

When a user sends a prompt to vLLM, the text becomes tokens. The model turns those tokens into embeddings and processes them through Transformer blocks. Attention lets tokens use context, MLPs transform each token representation, and the final layer produces logits for the next token.

Around that model loop, vLLM handles serving work: accepting API requests, batching active sequences, managing KV cache, running decode steps on the GPU, applying sampling settings, and returning generated text. If you understand both the Transformer path and the serving path, you can reason about model quality, speed, memory, and deployment.

Full request path

  • Client sends a chat/completions request.
  • vLLM validates the model name, messages, and sampling parameters.
  • The prompt is tokenized.
  • Prefill runs and creates KV cache for the prompt.
  • Decode generates one token per step for active requests.
  • Sampling chooses the next token from logits.
  • vLLM returns tokens as a stream or as a completed response.

Basic measurements

# Quick rough timing
time curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-0.5B-Instruct","messages":[{"role":"user","content":"Explain attention in 5 bullets."}],"max_tokens":200}'

What to explain in your capstone

  • Quality knobs: temperature, top-p, max tokens, prompt quality.
  • Speed knobs: model size, hardware, batching, prompt length, output length.
  • Memory pressure: model weights plus KV cache for active sequences.
  • Serving value: API compatibility, scheduling, batching, and cache management.

Final checkpoint: explain both paths in one story: prompt to tokens to Transformer logits to sampled tokens, and HTTP request to vLLM scheduler to GPU decode to API response.
